# Chapter 28b — npm & package.json

## What You Must Understand

The npm package ecosystem, `package.json`, dependencies, and running project scripts.

## The Core Idea

Chapter 28a's built-in modules (`fs`, `path`, `http`) ship with Node.js itself. But almost
every real project also needs code *other people* have already written and published —
Express (your next tracker topic) being the most immediate example. **npm** (Node Package
Manager) is how you download, manage, and use that third-party code, and **`package.json`**
is the file that keeps track of exactly what your project depends on.

## Starting a new project

```
mkdir my-project
cd my-project
npm init -y
```

This creates a `package.json` file — the "identity card" of your project:

```json
{
  "name": "my-project",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "dependencies": {}
}
```

(`-y` just accepts all the defaults instead of asking you questions one at a time — fine
for learning; you'd answer them thoughtfully for a real published package.)

## Installing packages

```
npm install express
```

Three things happen:

1. Express gets downloaded into a new `node_modules/` folder in your project.
2. `package.json`'s `"dependencies"` gets a new entry: `"express": "^4.18.2"` (or whatever
   the current version is).
3. A `package-lock.json` file is created/updated — this records the *exact* version of
   Express **and every package Express itself depends on**, so that anyone else who installs
   your project later gets byte-for-byte the same versions, not just "some version that
   matches roughly."

```javascript
// Now you can require/import it, exactly like a core module (Chapter 28a)
const express = require("express");
```

## `dependencies` vs `devDependencies`

```
npm install express            # a regular dependency — needed to actually RUN the app
npm install --save-dev nodemon # a dev dependency — only needed while DEVELOPING, not in production
```

- **`dependencies`** — code your running application genuinely needs (Express itself,
  a database driver).
- **`devDependencies`** — tools that help *you* while building it, but aren't needed once
  the app is actually running (a testing framework, a tool that auto-restarts your server
  on file changes).

This distinction matters once you deploy an app for real — production environments often
install *only* `dependencies`, skipping `devDependencies` entirely, to keep the deployed
app smaller and leaner.

## Understanding version numbers (semantic versioning)

`"express": "^4.18.2"` follows a convention called **semver**: `MAJOR.MINOR.PATCH`.

| Part | Changes when... |
|------|---------------------|
| **MAJOR** (4) | Breaking changes — code written for version 3 might not work anymore |
| **MINOR** (18) | New features added, but nothing existing breaks |
| **PATCH** (2) | Bug fixes only, no new features |

The `^` in front (`^4.18.2`) means "any version compatible with 4.18.2, up to but not
including 5.0.0" — i.e., accept new minor/patch updates automatically, but never
automatically jump to a new major version, since that's where breaking changes are
expected. This is why `package-lock.json` (mentioned above) matters so much: `package.json`
alone only specifies an *acceptable range*, while the lock file pins the *exact* version
actually installed, guaranteeing everyone on a project gets identical results.

## Running scripts

```json
"scripts": {
  "start": "node index.js",
  "dev": "nodemon index.js"
}
```

```
npm run dev
npm start
```

(`start` and `test` are special-cased — you can run them as `npm start`/`npm test` without
the word `run`; every other custom script name needs the explicit `npm run <name>`.) This
is how real projects standardize "how do I actually launch this thing" — instead of everyone
remembering their own command, `npm run dev` works identically for anyone who clones the
project.

## `node_modules` and version control

`node_modules/` can easily contain **tens of thousands of files** once a project has more
than a couple of dependencies (each package brings its own dependencies, and so on,
recursively). It should **never** be committed to Git — it's entirely regeneratable from
`package.json` + `package-lock.json` via a single `npm install`. Every real Node.js
project's `.gitignore` file excludes it for exactly this reason (you'll set this up properly
in Chapter 28c).

## `npx` — running a package without installing it permanently

```
npx create-react-app my-app
```

`npx` downloads and runs a package's command just once, without adding it to your project's
dependencies at all — useful for one-off project generators and command-line tools you
don't need to keep around afterward. Different from `npm install`, which is for packages
your *code* actually imports and depends on long-term.

## Hands-on Practice

**Initialize a project and manage dependencies.**

1. Create a new folder, run `npm init -y`, and open the resulting `package.json`.
2. Install a real package as a regular dependency (e.g. `express`) and a different one as a
   dev dependency (e.g. `nodemon`) — inspect how `package.json` records each differently.
3. Open `package-lock.json` and find the exact installed version of one of your packages —
   compare it to the version range (`^4.18.2`-style) shown in `package.json`, and explain
   the difference in your own words.
4. Add a custom script (e.g. `"dev": "nodemon index.js"`) to `package.json` and run it with
   `npm run dev`.
5. Delete your entire `node_modules/` folder, then run `npm install` with nothing else, and
   confirm everything reappears exactly as before — proving to yourself why it's safe to
   never commit that folder to Git.
